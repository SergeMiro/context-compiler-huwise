# Evaluation methodology

## Configurations

| | what the agent gets | what it is **not** |
|---|---|---|
| **A** `huwise` | the real Huwise MCP server (`https://mcp.huwise.com/mcp`) with its own four tools, names, descriptions and schemas as `tools/list` returns them (`evals/huwise_mcp.py`); the portal url is filled in by us | not Huwy: same free model and system prompt as B and C, not Huwise's model or prompt. Key of an ordinary user account (public data only), created 11.11.2026 |
| **0** `naked` (control) | generic catalog tools named like Huwise MCP's: `search_assets` (BM25 over title/description), `get_asset` (fields, types, description, 3 example records), `search_asset_records` (pass-through ODSQL, limit ≤ 100) | kept from the first experiments as a control; it is not the Huwise server |
| **B** `compiled` | `find_dataset` (ES + usage boost, short cards), `explain_dataset` (full card + joins), `query` (validated ODSQL) | — |
| **C** `optimized` | B + Context Optimizer: router (FAST recipe with 0 model calls / STANDARD / DEEP), grounded query (value hints, cache), evidence check (an unbacked number is not stated) | compression and tool parallelism are not enabled |

Same model, same system prompt, temperature 0, same tool-result truncation, same day, run back to back:
`manage.py eval --mode huwise` (A), then `--mode abc` (0, B, C). The model is the configured free OpenRouter model
(`CTXC_LLM_MODEL`, recorded on every run).

What a difference between B and C measures: the whole optimizer (routing + grounding + evidence), not context cards
alone. Between A and B: our cards **and** our search and validator versus Huwise's tools, with the same model.

## Question sets

- `education` (legacy, 30): written by hand together with the cards; **seen during development** → regression
  set, not a clean measure.
- `education_v2` (95): generated by `scripts/make_golden_v2.py` from templates and places taken from the API;
  shapes: counts by commune / department / académie / region / France, English questions, extra conditions
  (SEGPA, ULIS, internat, restauration, REP+), a dataset trap (lycées des métiers), averages (IPS), sums (bac),
  group-by (which académie has the most…), no-data questions, ambiguous places. Splits by slug hash:
  **dev 42 / val 27 / holdout 26**. The lab only sees failures outside the holdout (this cycle: the legacy set); the holdout is evaluated only for the final
  comparison. Limitation: the recipe parser was written before the v2 file, but both are by the same author in the same
  week, so the v2 phrasings are close to what the parser expects: **not an independent benchmark**. The FAST share
  on v2 is an upper bound for real user questions.
- Expected values: an independent reference ODSQL per question, executed on the API by `golden_refresh`
  (never typed by hand). The v2 references filter departments by `code_departement` (3 digits) while the recipe
  resolves `libelle_departement` — the two paths agree or the case fails.

## Scoring (no LLM judge)

`evals/runner.py: answer_ok` — numeric value within tolerance (counts 5 %, v2 averages and sums 1 %), numbers copied
from the question ignored; text answers by normalised inclusion; no-data by an explicit abstention. Also recorded per
case: right dataset, first query valid, steps, model calls, tokens, wall time, route, evidence status, abstention.

- **wrong and stated as fact** (`wrong_confident`): incorrect and not an abstention — the error that misleads.
- **evidence verified**: every number in the answer equals a value returned by a successful query.

## Statistics

Per configuration: accuracy with n; latency p50/p95 per question (wall time including model calls; linear interpolation); tokens; model
calls. Paired comparisons on the same questions: difference in percentage points with a **95 % paired bootstrap
CI** (2 000 resamples, fixed seed) and an **exact McNemar p-value** (`ctx/site.py`). One run per configuration: the
model's run-to-run variance is not captured by the CI (a limitation; repeated runs need more free quota).

## Quality gate for lab candidates

`lab/policy.json` (version `gate-2026-11-11.1`), fixed before any lab run: ≥ 1 fixed failing case, 0 broken control
cases, 0 new confident wrong answers, tokens ≤ +25 %. Accuracy and safety are hard constraints; latency/tokens are a
bounded trade-off. The gate is never adjusted after seeing results.
