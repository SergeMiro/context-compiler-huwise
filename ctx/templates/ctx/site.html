Pourquoi

Quatre pièges où un agent générique tombe

Le schéma du portail est riche, mais ses types sont piégeux. Chaque fiche les nomme avant que l'agent n'écrive sa requête.

clé de jointureTEXT ×3

Un département, trois formats

La Côte-d'Or s'écrit '021', '21' ou "COTE D'OR" selon le jeu.

− un seul format testé → 0 ligne
+ la fiche montre le vrai format
rentree_scolaireDATE

Années stockées en dates

Filtrer sur une année brute provoque une erreur de type de l'API.

− rentree_scolaire = '2025'
+ year(rentree_scolaire) = 2025
ips · ips_etabTEXT ≠ INT

Nombres stockés en texte

Les moyennes échouent, le tri suit l'ordre des chaînes.

− avg(ips) échoue · tri alphabétique
+ la fiche signale le type réel
nom d'académieAa ≠ AA

Casse différente

academie='DIJON' ici, libelle_academie='Dijon' là.

− filtre exact → aucun résultat
+ la fiche donne la casse attendue
Comment ça marche

Avant, pendant, après la question

Trois opérations sur une même table de fiches. Un LLM n'intervient qu'à la troisième, hors ligne.

  1. 01 · avant · hors ligne

    Compiler les fiches

    Context Compiler lit le portail et écrit une fiche par jeu de données.

    INSERT INTO fiches1 par jeu
  2. 02 · pendant · MCP

    Servir l'agent

    Votre agent interroge le serveur MCP : il reçoit les fiches déjà écrites et sa requête est vérifiée — sans LLM, rien n'est inventé.

    SELECT FROM ficheslecture seule
  3. 03 · après · évaluation

    Mesurer, améliorer

    Un LLM teste les fiches sur 30 questions de référence et propose des corrections ; une correction n'est gardée que si elle corrige sans rien casser.

    UPDATE fiches WHERE ✓sinon ROLLBACK

Sécurité

  • Chaque requête est isolée par portail, dans MariaDB, Elasticsearch et Neo4j — et c'est testé.
  • La clé API du client est transmise à l'Explore API, jamais stockée ni journalisée.
  • ODSQL en liste blanche : vrais champs seulement, limite ≤ 100, pas de commentaires.
  • Les champs personnels n'atteignent jamais les fiches ni le LLM.
  • Le journal garde l'outil, la latence et le code d'erreur — jamais la question ni la requête.

Pas fait — exprès

  • —Pas de LLM sur le chemin chaud.
  • —Pas de recherche vectorielle tant que les évals ne le demandent pas.
  • —Pas de LLM juge.
  • —Pas de LangChain ni LangGraph : la boucle agent tient en ~100 lignes.

Les idées derrière

Quatre idées de Karpathy, quatre briques du projet

Cliquez sur une idée pour voir d'où elle vient et comment Context Compiler l'applique.

AKAndrej Karpathy@karpathyGitHub
01Context engineeringLes fiches compilées : le bon contexte, court, au bon moment.
En juin 2025, Karpathy préfère « context engineering » à « prompt engineering » : “the delicate art and science of filling the context window with just the right information for the next step”.
Dans Context Compiler : d'abord une fiche courte (≤ 400 jetons) pour choisir le jeu ; la fiche complète seulement pour le jeu choisi — objet, fraîcheur, clés de jointure, formats et pièges.
Le post d'origine
02Software 3.0Construire pour les agents : des fiches et un llms.txt lisibles par un LLM.
Après le code écrit à la main (1.0) et les poids de réseaux de neurones (2.0), Karpathy décrit en 2025 un « Software 3.0 » programmé en langage naturel — et les agents comme un nouveau type d'utilisateur, pour qui la documentation doit être en markdown.
Dans Context Compiler : les fiches sont ce programme, versionnées comme du code (nouvelle version seulement si le texte change) ; llms.txt et {{ pages }} pages markdown sont générés pour le portail.
Conférence « Software Is Changing (Again) »Article « Software 2.0 »
03autoresearchLa boucle improve : proposer, tester, garder ou annuler.
Dans son dépôt autoresearch (2026), un agent modifie le code d'entraînement, lance une courte expérience et ne garde le changement que si la métrique s'améliore — sinon il revient en arrière.
Dans Context Compiler : improve propose une modification par fiche en échec, rejoue les 30 questions, et ne la garde que si elle corrige sans rien casser.
karpathy/autoresearch
04Génération ↔ vérificationL'agent génère, le validateur ODSQL vérifie avant le portail.
Dans la même conférence : l'IA génère, l'humain vérifie, et tout l'enjeu est d'accélérer cette boucle — avec un curseur d'autonomie et des sorties faciles à contrôler.
Dans Context Compiler : la vérification est automatique et sans LLM — vrais champs seulement, limite ≤ 100, indice si un champ est inconnu. improve a deux modes, « proposer » ou « auto » ; l'humain relit le diff dans l'admin Django.
Conférence YC AI Startup School
